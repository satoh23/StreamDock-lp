# streamdock-lp

デスクトップアプリ **StreamDock** のランディングページ。

- Frontend: React + TypeScript (Vite)
- スタイル: CSS Modules（配色トークンは StreamDock 本体の `theme.css` から移植）
- ホスティング: Cloudflare Pages

本体（アプリ本体のソース）は別リポジトリ。配布物は
[`satoh23/StreamDock-releases`](https://github.com/satoh23/StreamDock-releases) の Releases に置かれる。

## セットアップ

```sh
pnpm install
```

## 開発

```sh
pnpm dev        # http://localhost:5173
pnpm typecheck  # tsc --noEmit
pnpm build      # typecheck + dist/ を生成
```

## 公開 URL の設定（⚠ デプロイ後に必ずやること）

`.env` の `VITE_SITE_URL` が、`canonical` / OGP / `sitemap.xml` の絶対 URL の元になる。
**Cloudflare Pages のサブドメインが決まったら、ここを実際の URL に直すこと。**

ここが実際の URL と食い違うと、**X や Discord に貼ったときにカードの画像が出ない**
（クローラーは `og:image` の絶対 URL を取りに行くため）。

## プリレンダリングについて

`pnpm build` は次の 3 段階で動く。

1. `vite build` … 通常のクライアント向けビルド
2. `vite build --ssr` … `src/entry-server.tsx` を Node 向けにビルド
3. `node scripts/prerender.mjs` … ページ全体を HTML 文字列にして `dist/index.html` へ埋め込み、
   `sitemap.xml` / `robots.txt` を生成

これをやらないと `<div id="root"></div>` だけの HTML が配られ、JavaScript を実行しない
クローラーからは**中身が空のページ**に見える。新しい依存は入れていない
（`react-dom/server` は react-dom に含まれている）。

⚠ **ビルド時に描く HTML と、ブラウザでの初回描画は一致していないといけない。**
OS 判定・最新リリース取得・スクロール位置のような「ブラウザにしか無い情報」は
必ず `useEffect` の中で読むこと。`useState` の初期値に入れると hydration が失敗し、
React がページ全体を描き直す（＝プリレンダリングした意味が消える）。

## デプロイ（Cloudflare Pages）

| 設定項目 | 値 |
| --- | --- |
| Framework preset | None |
| Build command | `pnpm build` |
| Build output directory | `dist` |

`main` への push で自動デプロイされる。プルリクエストにはプレビュー URL が付く。

## ダウンロードボタンについて

`src/hooks/useLatestRelease.ts` が GitHub Releases API から最新版を取得し、
macOS の `.dmg` / Windows の `.exe` へ直接リンクする。**取得に失敗した場合は
Releases ページへのリンクにフォールバック**するため、API のレート制限や
リリース未公開の状態でもページは壊れない。

リリースを公開するたびに、このリポジトリを更新する必要はない。

## 文言のルール

ページ全体で用語を揃える。混ざると同じものを指しているのか分からなくなる。

| 語 | 指すもの | 例 |
| --- | --- | --- |
| **ツール** | 配信者が StreamDock に登録して管理する対象 | 「使うツールが 10 個でも 100 個でも」 |
| **アプリ** | StreamDock 自身 | 「配信者向けのツール管理アプリです」 |

⚠ 例外は**登録できる種別を Web ページと対比する箇所だけ**。ここは「実行ファイルか
Web ページか」の区別が要点なので「アプリ」を使う（例:「アプリのほか、Web ページも登録できます」）。
⚠ 「URL」は使わない（一般の配信者にとっては「Web ページ」のほうが通じる）。

⚠ **特定の配信サービスだけの用語で、両サービスに共通する概念を指さない。**
StreamDock は YouTube と Twitch の両方に対応しているため、片方の用語を使うと
もう片方のユーザーには自分の話に読めない。

| 使わない | 使う | 理由 |
| --- | --- | --- |
| スパチャ / スーパーチャット | **投げ銭** | YouTube 固有の名称。Twitch は Bits / チアー / サブスク |

⚠ 例外は**その機能が実際に片方にしか無いとき**。「レイド」は Twitch にしかない機能なので、
言い換えずにそのまま書く。

文体は「です・ます」で統一する。ただし次の 3 箇所だけ意図的に外している
（理由は各ファイルのコメントに記載。表記統一のつもりで戻さないこと）。

- ヒーローの見出し … 断言（「ツールが増えるほど、管理が楽になる。」）
- 悩みの声セクションのリード文 … 読み手の独白として書いているため言い切らない
- コメントビューアの見出し … 体言止め（「〜高機能コメントビューア」）

## 画像素材（スクリーンショット・動画）

`src/components/Screenshot.tsx` が OS の設定に追従して素材を差し替え、クリックで拡大表示する。

| 種類 | ファイル | いつ使われるか |
| --- | --- | --- |
| 静止画 | `<name>.png` | ライト |
| 静止画 | `<name>-dark.png` | ダーク（`dark` が true のとき） |
| 動画 | `<name>.webm` / `<name>.mp4` | ライト（`video` が true のとき） |
| 動画 | `<name>-dark.webm` / `<name>-dark.mp4` | ダーク |
| 動画の代わり | `<name>-still.png` / `<name>-dark-still.png` | poster ／ JS 無し ／「動きを減らす」設定 |

⚠ **ファイルを置く前に `dark` / `video` を true にしないこと。** 無いものを指すと
その環境で何も出なくなる。**置いてから true にする。**

### 静止画は CSS、動画は JavaScript で切り替える

静止画は `<picture>` の `media` だけで切り替わる（JS 不要・ちらつかない）。
動画は `<video>` の `<source media>` がブラウザで当てにならず、2 本置くと両方
ダウンロードされてしまうため、`matchMedia` で 1 本だけ選んでいる。
選ばれるまでは静止画を出すので、**JS が動かなくても中身は必ず見える**
（プリレンダリングした HTML にも静止画が入る＝クローラーからも読める）。

### 縦横比がばらばらな素材を並べるとき

一覧に並べる素材の縦横比が揃っていないときは、`frame` に枠の縦横比を渡す
（例 `frame="16 / 10"`）。カードの高さが揃い、中の素材は**切らずに収める**。
余った分は枠の地色になる。⚠ 枠が効くのは一覧だけで、拡大表示は常に素材そのものの
縦横比で出る。

⚠ **トリミングで縦横比を合わせるのは最後の手段にすること。** 横長のウィンドウで
撮った素材を 16:10 にすると幅を 30〜50% 削ることになり、「見せたい当のもの」が落ちる
（実例: 読み上げ設定はトグルが右端にあるので、幅を削るとトグルごと消える）。
⇒ **撮るときに縦横比を揃えるのが一番安い。**

⚠ 枠の中の素材には `min-height: 0` が要る。枠は grid なので、grid アイテムの
**自動最小サイズ**が効き、枠より縦長の素材だけ枠から溢れる（＝ contain のつもりが
cover になる）。理由は `Screenshot.module.css` の `.frameMedia` に書いてある。

### ⚠ 動く素材に GIF を使わない

GIF は 256 色しか使えないため、解像度を上げると急激に太る。実測（同じ 5 秒の録画）:

| 形式 | 解像度 | サイズ |
| --- | --- | --- |
| GIF | 400×250 | 404 KB |
| GIF | 800×500 | 652 KB |
| **MP4** | **1200×750** | **135 KB** |
| WebM | 1200×750 | 176 KB |

### 撮るときの決まり

- **画面収録の `.mov` を残しておく**（GIF に書き出したものを渡さない）。
  `.mov` は Retina の実解像度（例: 3024×1964）があり、GIF に落とすと 1/7 になる。
- ⚠⚠ **Retina のまま渡す（縮小して渡さない）。** 一覧のカードは 342px しかないので、
  素材の解像度がそのまま読めるかどうかを決める。実例: 固定のスクショだけ非 Retina
  （953px に画面まるごと）で渡されたため、他と同じ倍率では本文が 7px 相当になり、
  倍率を 77% まで上げる（＝もっと狭く切る）しかなくなった。
- ⚠⚠ **一覧に出す素材は「画面まるごと」ではなく「言いたい部分」を撮る／切る。**
  ウィンドウ全体を 342px に入れると倍率が 18% 前後になり、アプリの本文 13〜16px が
  5px 相当まで潰れて**何も読めないただの模様**になる。目安は**倍率 40% 以上**。
  ⚠ 目を細めて隣のカードと同じ絵に見えるなら、それは切り足りない合図。
- **ライトとダークで同じ操作・同じウィンドウ位置で撮る。** 揃っていないと、
  テーマを切り替えたとき別物に見える。
- ⚠ ダーク素材（`<name>-dark.png`）は**ライトと同じ縦横比で切る**。比が違うと
  枠の埋まり方がテーマ切り替えで変わる。⚠ 一方で**寸法が違っても画像は歪まない**
  ——`<img>` の width / height 属性より**実体の縦横比が優先される**（実測で確認）。
  属性が効くのは読み込み前の場所取りだけなので、食い違うと起きるのは歪みではなく
  レイアウトのズレである。
- **地が黒い素材はライトとダークで兼用してよい**（例: 配信画面に重ねたコメント）。
  その場合は `dark` を付けない。
- macOS のメニューバーは写ってよい（後で切る）。**壁紙が大きく写る撮り方は避ける。**

### 変換手順

```sh
SRC=~/Desktop/画面収録.mov
CROP="crop=W:H:0:76,scale=1200:-2"   # 76 = メニューバーの高さ。素材ごとに実測する

ffmpeg -i "$SRC" -vf "$CROP,fps=30" -c:v libx264 -crf 26 -preset slow \
  -pix_fmt yuv420p -movflags +faststart -an public/images/<name>.mp4
ffmpeg -i "$SRC" -vf "$CROP,fps=30" -c:v libvpx-vp9 -crf 36 -b:v 0 -row-mt 1 \
  -an public/images/<name>.webm
ffmpeg -i "$SRC" -vf "$CROP" -frames:v 1 public/images/<name>-still.png
```

静止画の縦横比を揃えるときは、下の余白だけを落とす:

```sh
python3 -c "
from PIL import Image
im = Image.open('元画像.png'); w, h = im.size
im.crop((0, 0, w, round(w / 1.6))).save('public/images/<name>.png')"
```

⚠ `sips -c` は**中央基準**で切るので上端も削れる。上を残したいときは使わない。

### 権利まわり

⚠ **実在の視聴者名・アイコン・コメントを写さないこと**（第三者の投稿とアイコン画像の
無断利用になる）。テスト用アカウントのダミーで撮影する。

⚠ 他社アプリのアイコンが UI に写り込むのは、事実の説明に必要な範囲なので問題ない
（VOICEVOX / わんコメの規約を確認済み）。ただし**ロゴを並べた「対応ツール一覧」は
作らない**（提携の誤認を招く）。フッターの商標注記と VOICEVOX のクレジットは消さないこと。
